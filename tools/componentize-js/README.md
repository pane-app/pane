# componentize-js: Pane's JS/TS toolchain

Builds JavaScript and TypeScript commands into WASI 0.3-only components. The
componentizer is upstream [componentize-qjs](https://github.com/andreiltd/componentize-qjs)
at a pinned commit, vendored into this repository with a small patch queue
applied in its source — not a fork. Authoring and the prerequisites are
described in [guests/README.md](../../guests/README.md); this page is for
maintaining the toolchain.

- [`pins.json`](pins.json): the componentize-qjs commit and archive digest,
  the patch order, the Rust nightly and the wasi-sdk release with per-host
  archive digests. (The x86_64 Linux and Windows digests were checked against
  downloads; the others are GitHub's recorded asset digests.)
- [`componentize-qjs/`](componentize-qjs): the vendored source tree, the
  patch queue applied in it; see [its README](componentize-qjs/README.md)
  for what differs from upstream. Its `crates/core` is a member of the
  repository's workspace; `crates/runtime` (built only for
  `wasm32-wasip3`, by `pane_js.py wasm-parts`) is excluded from it.
- [`patches/`](patches): the queue, as it was last applied to the vendored
  source (0003 is retired there by the Wasmtime 49 pin; `pins.json` records
  that). Applied in order with `git apply` when the tree was vendored.
- [`wasm-parts/`](wasm-parts): the committed `runtime.wasm` (the QuickJS
  runtime for `wasm32-wasip3`) and wasi-sdk 34's WASI 0.3 `libc.so`, with
  what built them and their digests in `wasm-parts.json`. They are
  host-independent: built once (`componentizer.yml`'s `Wasm parts` job), and
  embedded by `pane-build` (its `componentizer` feature), so every JS/TS
  build of the repository uses exactly these bytes. The vendored runtime
  crate carries the `Cargo.lock` that build resolved (generated by CI,
  committed in the tree): the pinned nightly, the wasi-sdk, the lock and
  the build's fixed paths are what let a rebuild reproduce those bytes,
  which `check-parts` compares.
- [`pane_js.py`](pane_js.py): the maintenance commands — `wasm-parts <dir>`
  (builds the runtime with the pinned nightly and wasi-sdk, and copies the
  libc), `componentizer <dir>` (builds the standalone componentizer, the
  `p3_build` example of the vendored crate, with the repository's stable
  Rust) and `check-parts <dir>` (compares the committed parts against a
  fresh build). Building a package is no longer its work: `pane-build`
  does that (#218), with Node.js and npm alone, and `cargo xtask js-guests`
  rebuilds the committed samples with it. When #219's `@pane-app/cli`
  packages retire `componentizer.yml`, this script goes with it.
- [`package.json`](package.json) / [`package-lock.json`]: esbuild 0.28.2 and
  TypeScript 7.0.2, the versions of record that the samples' lockfiles must
  pin (`cargo xtask ci-lints` checks that they do).

## Every platform

`pane-ext` will ship the componentizer for Windows, macOS and Linux on x64
and arm64 (spec [#128](https://github.com/pane-app/pane/issues/128)), so
[`componentizer.yml`](../../.github/workflows/componentizer.yml) builds it
for all six whenever this folder changes, or on demand. The wasm parts are
the same everywhere, so one Linux job builds them, records their digests —
and compares them with the committed `wasm-parts/`, which the repository's
builds embed, so those cannot drift from the vendored source. Then each
platform runs `pane_js.py componentizer`, which checks those digests and
builds `p3_build` against them with the stable Rust alone (no nightly, no
wasi-sdk). It uploads the binary as `componentizer-<target>`, rebuilds the
JS/TS samples through pane-build's build with that binary
(`PANE_COMPONENTIZER`, the same path an installed Pane's development mode
spawns), and runs `pane-core`'s TypeScript sample checks and
package-install tests on the result.

The first run (37840978895, 2026-10-08) passed on all six with nothing
platform-specific in the build. Each runner image already has rustup, the
MSVC or Xcode linker, Python and Node. Building `p3_build` took 5–10 minutes
cold (20 on `macos-15-intel`), and the sample componentized in under a second
(1.5 seconds on `macos-15-intel`). Wasmtime,
which the componentizer runs to snapshot the runtime, works on Windows
arm64 (`windows-11-arm`) as on the other five. macOS x64 runs on
`macos-15-intel`.

## Updating

1. Change the commit and archive digest in `pins.json` (and the nightly or
   wasi-sdk pins, if needed), and re-vendor: apply the queue (rebased
   wherever it no longer fits) to the new source in
   `componentize-qjs/`, keeping each patch's rationale as comments where
   the queue is applied in-source, and updating the pins of
   `componentize-qjs/crates/core/Cargo.toml` to the repository's.
2. Rebuild the wasm parts and commit them:
   `python tools/componentize-js/pane_js.py wasm-parts
   tools/componentize-js/wasm-parts` (which also rewrites
   `wasm-parts.json`), then `cargo xtask js-guests` and commit the rebuilt
   `guests/prebuilt/`.
3. Run `cargo xtask ci`, and commit the patches, pins and the rebuilt
   `guests/prebuilt/`.

Any change to these files or to the sample sources makes the prebuilt-samples
check (`cargo xtask js-guests --check`, run by CI) report the prebuilt
components as stale until they are rebuilt. The upstream candidates in the
validation report (the per-instance reseed, the context-slot fix and a
`wasm32-wasip3` build option) would each shrink the queue if accepted
upstream; the Wasmtime 49 upgrade already retired one patch (0003).
