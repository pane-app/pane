# Pi extension process arrangement (Q23)

Verified 2026-09-27 against pinned Pi commit `2b0a123de98318c2ff8069661721ce0c3794c34e`. This concerns conventional coding-agent extensions, not the separate Chord runtime. Source inspection only; no performance measurements. The older temporary source cache was unavailable, so the three cited source files were downloaded again to `%TEMP%/kyoko-pi-q23-audit`.

## Execution arrangement

Pi imports an extension module with `jiti.import()`, obtains its factory, and directly awaits `factory(load.api)`. The runner directly invokes and awaits registered handlers. Consequently, conventional extension JavaScript executes inside the Pi application's process and JavaScript execution thread; the host does not allocate a worker thread or subprocess for each extension. Sources: [module import and initialization](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/extensions/loader.ts#L479), [representative event dispatch](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/extensions/runner.ts#L927).

This is not a claim that Pi has no operating-system threads or subprocesses. An extension can explicitly start external work. Pi supplies `exec` through `execCommand`; its authoring documentation explicitly discusses author-created processes, sockets, watchers and timers. Sources: [exec implementation](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/extensions/loader.ts#L381), [resource lifecycle](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/docs/extensions.md#respect-the-runtime-lifecycle).

## Loading, reload and failures

Factories initialize when the enabled extension set loads; commands and handlers subsequently execute on invocation. Pi tells authors to defer long-lived work until `session_start` or the command/tool requiring it, and release resources in `session_shutdown`. Reload replaces the extension runtime within the application; authors must not reuse old runtime state afterward. It is not termination/recreation of one host-assigned worker per extension. Source: [author lifecycle documentation](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/docs/extensions.md#respect-the-runtime-lifecycle). See also the previously verified [reload implementation research](pi-reload.md).

Pi catches many handler failures and reports them while continuing where possible. Direct same-thread execution nevertheless means a synchronous extension loop can block the shared JavaScript thread; process-fatal failure affects the application, without a separate extension process protecting it. These are consequences of the execution arrangement, not a claim that every exception terminates Pi. Sources: [dispatch error handling](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/extensions/runner.ts#L947), [documented failure handling](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/docs/extensions.md#errors-and-cleanup).

## Relevance to this launcher

Pi is a precedent for trusted, flexible extension APIs and direct in-process composition. It is not a precedent for one Node worker per extension. Our Rust/GPUI desktop host can keep its UI process separate from a managed Node extension process while retaining Pi's trusted capability model. That would be an adaptation. No source review establishes which candidate arrangement uses less memory in our workload; benchmark active/idle extensions and UI responsiveness before making resource claims. Q23 subsequently accepted the Raycast-style shared Node helper/worker arrangement for our launcher; see [ADR 0009](../adr/0009-shared-node-helper-with-extension-workers.md).
