# VS Code dependency disabling and removal — Q27

Researched 2026-09-27 against official source pinned to `4336606aa949efdcddb89b3db3e216562730b2bf`, the revision used for [Q26](vscode-extension-dependencies.md). Source inspection, not an installed-client experiment. Let extension A require extension B. The user subsequently chose this normal disable/uninstall-together direction in Q27; see [extension policies](../extension-policy-proposal.md).

## Normal UI behavior

- **Disable B:** when enabled dependents exist, the UI offers **Disable All** or cancel. Accepting recursively passes A and B through the same requested global/workspace disable operation. A is explicitly disabled in stored user state; this is not just a temporary dependency-unavailable flag. [Prompt/cascade](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts#L3144), [stored state setter](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts#L408), [global/workspace persistence](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts#L694).
- **Re-enable B:** the enable traversal follows B's own dependencies and extension-pack members, not reverse dependents. Therefore an ordinary A previously disabled through that cascade does **not** automatically re-enable merely because B does. The user can enable A; enabling A also includes its dependencies. This is a source-derived conclusion for ordinary dependency A→B, excluding an independent pack relationship that could also select A. [Enable traversal](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts#L3130), [service recursion](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts#L309).
- **Uninstall B:** the normal UI collects installed dependents recursively and offers **Uninstall All** or cancel. Acceptance removes A too; it does not leave A installed with a missing-dependency badge. The uninstall collection does not filter dependents by enabled state. [Collection and prompt](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts#L2875), [execute uninstall set](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts#L2935).
- **Reinstall B afterward:** this normal removal path has uninstalled A. No reverse-dependent reinstall mechanism is established by these flows; do not promise that restoring B restores A. A must be installed again through an explicit install or another package relationship. This is different from our proposed preserve-installed-but-unavailable behavior.

## Important distinctions and limits

- The underlying uninstall service rejects a removal set that leaves installed dependents. Its explicit `donotCheckDependents` option bypasses the guard; it is not a normal UI “remove B only” option. This audit does not assert which CLI flags map to it. [Bypass](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts#L873), [guard](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts#L942).
- VS Code also has a **computed** `DisabledByExtensionDependency` state when an otherwise user-enabled extension has an installed dependency that is disabled. That state is distinct from the stored global/workspace disabled state assigned by the UI cascade. Recomputing dependency availability can clear the computed state, whereas explicit user-disable state remains. [Computed state](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts#L500), [dependency computation](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts#L606).
- That computation filters installed dependencies and is **not** a general missing-dependency detector. If an unknown dependency reaches activation, the extension activator records a failed operation and reports a missing-dependency activation error. Do not equate all absent/disabled cases with one automatically recoverable UI state. [Activation failure](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/api/common/extHostExtensionActivator.ts#L311).
- No claims here about extension-owned data deletion/preservation, exact reload timing, or seamless recovery after a forced/manual missing-dependency situation; those were not tested. Profiles, extension packs, remote hosts, and special built-ins add branches beyond the ordinary A→B case.

## Launcher implication

VS Code supports warning users about affected dependents and preventing their execution without working requirements. It does **not** establish the proposed launcher behavior of retaining dependent extensions and automatically restoring their availability when the missing requirement returns. That proposal is a deliberate product choice: keep the user's enabled/disabled preference separate from computed dependency availability. The user subsequently selected the VS Code-style normal flow, superseding our earlier retained-unavailable proposal.
