# Tinycast: source audit for a cross-platform, extensible launcher

Research date: 2026-09-27. Inspected commit: [`6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9`](https://github.com/abue-ammar/tinycast/tree/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9). Read official documentation and implementation; did not build or execute repository code. “Measured” below describes upstream evidence, never a measurement made during this audit.

## What it actually is

Tinycast is a native **macOS launcher**, with app search, clipboard history, calculator, snippets, window management, notes, calendar, AI and Raycast extensions. Its application target is explicitly macOS 26.0+, using Swift 6. It is a useful behavioral reference, but it is not an existing cross-platform foundation. [README](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/README.md), [build targets](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/project.yml).

Its architecture separates pure policy, platform effects, observable state and views. However, `AppCore.shared` owns the long-lived built-in feature stores, services and coordinators. The palette is an AppKit `NSPanel` hosting SwiftUI. **Inference:** small resource use and a small architectural kernel are different goals; Tinycast pursues the former while retaining many built-in features. Copying its organization wholesale would not produce the requested Pi-like plugin core. [Architecture](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/docs/architecture.md).

## The valuable extension design

An extension contains a manifest (`package.json`), prebuilt CommonJS command bundles and assets. Tinycast supplies React, a custom React reconciler, a Raycast API implementation, and Node/web shims. JavaScriptCore evaluates commands; the reconciler emits a JSON render tree; native SwiftUI renders lists, grids, details and forms. Callback handles route user events back to JavaScript. This separates extension logic from the host renderer without embedding a browser. [Extension architecture](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/docs/features/extensions.md), [reconciler](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Scripts/raycast-runtime/src/reconciler.js).

`ExtensionRuntime` confines its `JSContext` to a serial queue. JSON and plain render values cross the boundary. Async host operations avoid blocking the UI; synchronous filesystem/process shims execute on the JavaScript queue. Shutdown cancels timers and host tasks, changes a generation identifier, discards the context and closes file handles. Replies with an obsolete generation are ignored. This is a useful lifecycle model for preventing old work from corrupting a replacement session. [Runtime implementation](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Tinycast/Features/Extensions/Service/ExtensionRuntime.swift).

The extension runtime is lazy. A foreground command reads its bundle from disk; stopping it discards the runtime context. Scheduled background commands borrow the foreground lane, while menu commands have a separate transient runtime. There is an explicit rescan operation. **I did not find a developer file watcher or state-preserving hot-module reload in the inspected manager/runtime.** Fresh execution on the next command launch is not the same feature as automatic development reload. [Manager implementation](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Tinycast/Features/Extensions/Service/ExtensionManager.swift), [menu lifecycle](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Tinycast/Features/Extensions/Service/ExtensionMenuBarManager.swift).

## Installation and compatibility are substantial subsystems

Installing a built extension copies only its manifest, command bundles and assets, omitting `node_modules` and source maps. Catalog discovery filters for macOS compatibility. Source installs download into a temporary workspace, resolve an installed package manager, build, then copy the produced files. The installer invokes `ray` directly when available and has a fallback for packages using their own build script. A five-minute process timeout bounds build commands. This means **no Node runtime needed to run a prebuilt extension** does not mean **no Node/toolchain needed to build an extension**. [Catalog](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Tinycast/Features/Extensions/Service/ExtensionCatalog.swift), [installer](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Tinycast/Features/Extensions/Service/ExtensionInstaller.swift).

Raycast compatibility is partial. The developer docs explicitly retain gaps around Raycast-hosted services, its OAuth proxy, raw TCP/TLS, streaming HTTP and interactive process stdin. The reported sample is 32 of 37 extensions and 114 of 147 view commands booting/rendering; the docs warn that this predates OAuth changes and needs remeasurement. It is not evidence that those commands complete their workflows or that an arbitrary store extension works. [Compatibility and measurement notes](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/docs/features/extensions.md#whats-supported).

There is observable documentation drift: the website compatibility page lists WebSocket and live `spawn` output as unavailable, while developer documentation describes both, and source contains a `URLSessionWebSocketTask` bridge. Prefer pinned source and targeted tests over the public compatibility checklist. [Website checklist](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/website/content/docs/extensions/compatibility.md), [WebSocket implementation](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Tinycast/Features/Extensions/Service/ExtensionWebSocketBridge.swift).

## Resource and trust claims need precise boundaries

The README advertises under 100 MB RAM; contributing rules require idle/peak measurements and return to baseline. The testing document reports a historical release binary of 3,655,736 bytes and 40–80 MB resident memory, but also says launch time, allocation counts and RSS had not been captured as numbers. These are upstream snapshots/claims with inconsistent measurement documentation, not reproducible cross-platform budgets. The current checkout was not profiled here. [Contribution requirements](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/CONTRIBUTING.md), [testing and performance notes](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/docs/testing.md).

The README's zero-third-party-dependencies language needs qualification: the extension runtime build manifest declares React, `react-reconciler`, esbuild and `@raycast/api`, and its generated bundle is committed into the application. That differs from having no third-party code. JavaScriptCore itself comes from the operating system on macOS; its zero-vendored-engine-size advantage does not automatically transfer to Windows/Linux. [Runtime package manifest](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Scripts/raycast-runtime/package.json), [runtime build](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Scripts/raycast-runtime/build.mjs).

Extensions execute in the application process. The app explicitly disables App Sandbox, and its Node shims expose filesystem and process operations. A separate JS context therefore provides lifecycle separation, **not an OS security boundary**. The native shims depend on Darwin, CommonCrypto, CryptoKit and macOS APIs. **Inference:** a new public extension ecosystem should decide whether it trusts arbitrary local code or enforces scoped capabilities; inheriting this model silently would be a product decision. [Entitlements](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Tinycast/Tinycast.entitlements), [native shims](https://github.com/abue-ammar/tinycast/blob/6fc6aa1b909ca24e3cd25e35c078a7c808ca34a9/Tinycast/Features/Extensions/Service/ExtensionNodeShims.swift).

## Recommendations inferred from the audit

1. Reuse the **idea** of declarative extension views and a narrow host API; define your own small, versioned contract first.
2. Keep OS adapters explicit: application discovery, global shortcuts, clipboard, text insertion, secrets and window control are separate portability problems.
3. Define reload as a lifecycle transaction: stop admission, cancel owned work, revoke callback generation, dispose resources, load a new instance, and restore only explicit serialized state.
4. Measure total application plus extension-worker memory, idle CPU, startup and p95 input-to-result latency with specified workloads on all supported OSes.
5. Treat Raycast compatibility as a separately scoped adapter with a conformance matrix. It should not define the core API or delay the first useful launcher.
6. Decide whether the first release is a small launcher with optional features, or a broad productivity suite. Tinycast demonstrates that those are different scope commitments.
