# JS/TS guest backends for a WASI 0.3-only Wasmtime host

Source review: 2026-09-28. This is a bounded check of ComponentizeJS, StarlingMonkey, Jco, the ComponentizeJS reboot, and Wasmtime's published adapter implementation. No engine was built for this review. It preserves the accepted requirements: JS/TS and Rust at launch, WASI 0.3-only, and real host capabilities. It does not establish absence of every possible third-party backend.

**Finding:** none of the inspected alternatives establishes a ready replacement for the tested QuickJS guest that removes its WASI 0.2 runtime dependencies. Current Jco's p3 hosting support is real, but is a different direction of execution. The most concrete next implementation investigation remains the existing QuickJS runtime dependency boundary; changing to stock StarlingMonkey would add an async guest-bindings gap as well.

The existing [measured JS probe](wasi03-js-spike/README.md) already runs Fuse.js, Zod, and a real p3 async clock in Wasmtime, while its final component imports 18 p2 interfaces. That measured result is stronger evidence about this exact workload than a tool's general “p3 support” statement.

## Candidate comparison

| Candidate | What the inspected sources establish | Consequence for this project |
| --- | --- | --- |
| Jco `transpile` plus `preview3-shim` | Converts an existing component to JS glue/core Wasm for a JS host; the shim implements WASI host facilities. | Useful when Node/browser hosts a component. It does not turn the JS extension and engine into a p3-only component for Wasmtime. |
| Jco `componentize` | Current source selects QuickJS or StarlingMonkey backends. Package dependencies are `componentize-qjs ^0.4.5` and `@bytecodealliance/componentize-js ^0.22.0` (with a legacy SM fallback). | A convenient frontend to the engines considered here, not a separate backend solving their runtime imports. |
| Stock ComponentizeJS + StarlingMonkey | A real JS-to-component tool, but StarlingMonkey documents p2 core builtins and ComponentizeJS's native async guest ABI paths remain unimplemented in inspected code. | Not an off-the-shelf p3 replacement; moving here introduces more work than removing QuickJS's already-demonstrated legacy runtime dependencies. |
| `dicej/componentize-js` reboot | Implements native async imports/exports, streams and futures through `wit-dylib`; ships p3 CLI/HTTP examples. Runtime build, adapter, and example host still involve p2. | A credible future engine/bindings candidate. The examples do not prove p3-only output, and this review did not build or inspect its final component. |
| Wasmtime's preview1 component adapter | Explicitly translates preview1 to p2; generated bindings point at p2 WIT. | Its command/reactor/proxy variants do not supply the needed p1-to-p3 migration. |

## ComponentizeJS and StarlingMonkey

StarlingMonkey's README explicitly targets WASI 0.2.0 for core builtins, including its event loop and web APIs. Its host implementation directory is `host-apis/wasi-0.2.0`. A modular runtime and custom host APIs are useful extension points, but are not a completed p3 port. [Pinned README](https://github.com/bytecodealliance/StarlingMonkey/blob/fb47e0e771fb8538b8cf2a41c24e534cca518e44/README.md), [host implementation](https://github.com/bytecodealliance/StarlingMonkey/tree/fb47e0e771fb8538b8cf2a41c24e534cca518e44/host-apis/wasi-0.2.0).

ComponentizeJS accepts JS promises from exports by running its internal event loop to completion while exposing synchronous component functions. Its documented imports are synchronous. Source corroborates this: async function-kind/ABI cases contain `todo!()`, binding generation explicitly sets `is_async(false)` and `canonical_abi_async(false)`, and the export wrapper comments distinguish JS promise handling from a real p3 async export. This is a concrete guest-generation limitation, regardless of Jco's host-side async support. [Async documentation](https://github.com/bytecodealliance/ComponentizeJS/blob/4d812f5a7b524cea5bcfd565cac55f3fab876a57/README.md#async-support), [guest bindgen implementation](https://github.com/bytecodealliance/ComponentizeJS/blob/4d812f5a7b524cea5bcfd565cac55f3fab876a57/crates/spidermonkey-embedding-splicer/src/bindgen.rs#L900).

The README offers `disableFeatures` and says disabling everything creates a component without WASI dependence. That can serve intentionally pure computation, but does not port clocks, I/O, HTTP or native async imports. A capability-first extension SDK must implement the intended facilities, not count their removal as completion. The same README warns that its returned import list excludes engine imports and recommends direct component analysis. [Feature options and import-list warning](https://github.com/bytecodealliance/ComponentizeJS/blob/4d812f5a7b524cea5bcfd565cac55f3fab876a57/README.md#api).

## ComponentizeJS reboot: promising, still a different integration project

The `dicej/componentize-js` README currently marks native async imports/exports, streams/futures, resources and arbitrary WIT types as implemented. It describes a `wit-dylib`/Rust embedding intended eventually to integrate with StarlingMonkey. Web/Node API integration, CI execution of tests/examples and generated TypeScript bindings remain unchecked checklist items. Treat this as a source prototype with relevant functionality, not as the old ComponentizeJS async limitation. [Pinned status](https://github.com/dicej/componentize-js/blob/ffa945621842c27c4dd992bed54ecc4375de5b49/README.md).

Its build uses `wasm32-wasip2` for the runtime and wasi-sdk libraries, and includes a preview1 reactor adapter. The componentizer links that adapter. Its p3 example test harness installs both `wasmtime_wasi::p2::add_to_linker_async` and `wasmtime_wasi::p3::add_to_linker`. Together these show legacy integration remains present; neither a p3 example world nor the compiler target alone proves the final import graph. No p3-only artifact was validated here. [Build script](https://github.com/dicej/componentize-js/blob/ffa945621842c27c4dd992bed54ecc4375de5b49/build.rs), [component assembly](https://github.com/dicej/componentize-js/blob/ffa945621842c27c4dd992bed54ecc4375de5b49/src/lib.rs#L163), [example host](https://github.com/dicej/componentize-js/blob/ffa945621842c27c4dd992bed54ecc4375de5b49/tests/examples.rs#L72).

## Adapter boundary

Wasmtime's current `wasi-preview1-component-adapter` describes its output as importing p2. Its source generates bindings from `../wasi/src/p2/wit`, and the proxy branch names `@0.2.12` clock imports. The inspected implementation is consequently not a ready p1-to-p3 adapter. This review did not identify a documented official p2-to-p3 guest adapter in the checked Wasmtime implementation or Jco guest backend paths. That is a scoped finding, not a claim that no such work exists anywhere. [Adapter README](https://github.com/bytecodealliance/wasmtime/blob/11eac9de8693e1a69f86815d1a58918edd5c1785/crates/wasi-preview1-component-adapter/README.md), [actual binding sources](https://github.com/bytecodealliance/wasmtime/blob/11eac9de8693e1a69f86815d1a58918edd5c1785/crates/wasi-preview1-component-adapter/src/lib.rs#L53).

A host that implements p2 and p3, or implements p2 operations internally using shared facilities, still accepts p2 guest imports. Wasmtime's p2 module explicitly exposes p2 host implementations; its use of Rust async does not alter their guest interface. Similarly, Jco's JS shims are host implementations, not Wasm guest adapter artifacts. [Wasmtime p2 host contract](https://github.com/bytecodealliance/wasmtime/blob/11eac9de8693e1a69f86815d1a58918edd5c1785/crates/wasi/src/p2/mod.rs#L114).

## Recommendation and complexity

Continue the bounded QuickJS runtime-port investigation before switching engines. This is an engineering recommendation based on the local probe already demonstrating the required JS libraries and native async call. It does not select a production fork or promise that its dependency boundary is small.

- **QuickJS runtime integration: medium to high, scope still to establish.** Inventory actual engine core imports and execution paths; separate snapshot/build needs from runtime needs; implement required clocks, randomness, diagnostics and filesystem/module behavior over p3. Preserve legitimate errors and permissions. Avoid a universal trap-stub “solution.”
- **Stock StarlingMonkey migration: high.** In addition to migrating runtime builtins/event-loop I/O, implement missing native async guest bindings. Its broader web API surface may later justify this work, but offers no shortcut demonstrated here.
- **Reboot migration: medium to high, unmeasured.** Native async bindings already exist in source, but p3 runtime isolation, build reproducibility, library compatibility and web API coverage need validation. It is a useful alternative if the QuickJS boundary proves impractical.
- **General p1/p2-to-p3 guest adapter: high.** Resource ownership, sync/poll-to-native-async behavior, filesystem and stream error/completion semantics make this a compatibility subsystem. No inspected ready artifact removes that work.

Any candidate must produce an inspectable final component whose complete external WASI import graph is 0.3-only; run the existing Fuse/Zod/async-clock workload under a host that exposes only p3; then exercise the capabilities being claimed, including denied access, errors, cancellation and resource cleanup. Final import inspection and functional tests must both pass. A p3 WIT world, a JS Promise, or a host supporting p3 individually is insufficient evidence.
