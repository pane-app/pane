# VS Code activation failure and rollback

Researched 2026-09-27 for Q31. Source inspection only; no extension was executed and no failure was injected. Source links are pinned to `4336606aa949efdcddb89b3db3e216562730b2bf`. This note concerns new extension code failing after an update/reload, separately from package installation failure and a fatal extension-host process crash.

## Import and activation errors

The extension service loads the selected extension's CommonJS/ESM module and context before calling its optional `activate` function. A synchronous exception or rejected activation promise propagates through that activation operation. This covers startup/import failure as well as failure inside `activate`; it does not cover every arbitrary future exception an extension might cause. [Module loading and activation](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/api/common/extHostExtensionService.ts#L436), [activation wrapper](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/api/common/extHostExtensionService.ts#L528).

The activator catches the rejection, records a `FailedExtension`, reports the activation error to the host and writes error logs. Required dependents fail activation when their dependency has failed. Activation operations are cached by extension ID, so merely repeating the activation request against the same activator reuses the failed operation; this is not an automatic retry loop. The inspected failure handler does **not** select or reactivate an older installed version. That is a source-level conclusion about this path, not a claim that VS Code has no rollback machinery anywhere. [Failure handler](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/api/common/extHostExtensionActivator.ts#L385), [operation reuse](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/api/common/extHostExtensionActivator.ts#L217), [failed dependency](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/api/common/extHostExtensionActivator.ts#L366).

## Two different recovery paths

**Whole local extension host exits:** desktop VS Code can restart the extension host automatically. After repeated crashes it offers manual restart and Extension Bisect in a production build. Its message identifies the repeated-crash threshold as three within five minutes. A version-mismatch exit instead offers relaunching VS Code. Restarting that process is distinct from replacing a broken extension with its previous code version; the inspected crash handler does not do the latter. [Desktop host crash handling](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts#L142).

**Package installation fails:** the package manager has a separate rollback path. If an installation group fails, it can cancel pending tasks and uninstall successfully installed members whose root task or required installation group failed, using version-only uninstall tasks. This is install-transaction cleanup; it is not evidence of automatic rollback after extension startup code throws. [Installation failure handling](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts#L452).

## User-controlled version recovery

The official extension-management manual documents selecting **Install Another Version** from an extension's context menu and choosing an available version. It also documents per-extension automatic-update controls. These supply a manual recovery route when a published version is broken; the availability of earlier versions does not establish rollback of saved data or extension side effects. [Official extension management manual](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace#install-an-extension).

## Implication for the launcher

VS Code supports the proposed distinction: report a startup/activation failure and let the developer or user recover; treat package-install failures and runtime-process restarts separately. Its inspected activation path is not a precedent for automatic restoration of previously working code after startup failure. The user subsequently accepted Q31: report startup failure with Retry/logs and no automatic version rollback. Manual version selection remains a separate Q32 proposal. A launcher Retry button would be our recovery interface, not a claim that VS Code exposes that exact per-extension button or automatically retries the failed activation.
