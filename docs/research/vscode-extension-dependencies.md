# VS Code extension dependencies — Q26

Researched 2026-09-27. Official manifest documentation plus source pinned to `4336606aa949efdcddb89b3db3e216562730b2bf` (GitHub `main` resolved during this audit). Source inspection only; no installed-client experiment. Q26 subsequently accepted the launcher's required/optional installation recommendation; see [extension policies](../extension-policy-proposal.md). The comparison does not imply adopting every VS Code behavior.

## Findings

- **Functional dependencies:** `extensionDependencies` lists other extension IDs such as `publisher.name`. It differs from npm `dependencies`, which supplies ordinary Node libraries. **Extension packs** list extensions to install together; members should remain independently manageable and should not be functional dependencies of the pack. [Manifest documentation](https://code.visualstudio.com/api/references/extension-manifest#fields), [pack documentation](https://code.visualstudio.com/api/references/extension-manifest#extension-packs).
- **Automatic installation:** the normal installation pipeline recursively collects missing dependencies and pack members from the Marketplace, then installs them. Already-installed dependencies are excluded by extension ID. Marketplace availability and install options matter; this is not a guarantee that any arbitrary offline package resolves every dependency. [Installation pipeline](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts#L393), [recursive collection](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts#L648).
- **Version constraints:** the manifest schema accepts extension identifiers, not an npm-style map of dependency version ranges. Collection selects a compatible Marketplace version for VS Code/platform and skips installed IDs; it does not implement consumer-specified ranges such as `file-search: ^2`. Therefore our proposed dependency-version checking would be an additional design choice, not something directly copied from this mechanism. [Schema](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensions/common/extensionsRegistry.ts#L476), [selection](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts#L658).
- **Disabled dependencies:** enabling an extension recursively includes installed dependencies and pack members in the enable operation. There are eligibility restrictions, but VS Code is **not** precedent for a universal rule that previously disabled dependencies stay disabled. Our existing decision that a programmatic call never silently enables an extension is a distinct rule. [Enablement service](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts#L309), [recursive filtering](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/services/extensionManagement/browser/extensionEnablementService.ts#L346).
- **Disabling/uninstalling a dependency:** the UI detects dependent extensions and offers to disable or uninstall them together, or cancel. The underlying uninstall service rejects removal when dependents would remain, except for explicit options bypassing the check. This protects the dependency relationship rather than silently leaving a broken active consumer. [Disable flow](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts#L3130), [uninstall flow](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/workbench/contrib/extensions/browser/extensionsWorkbenchService.ts#L2917), [uninstall guard](https://github.com/microsoft/vscode/blob/4336606aa949efdcddb89b3db3e216562730b2bf/src/vs/platform/extensionManagement/common/abstractExtensionManagementService.ts#L942).

## Implications for our launcher

VS Code supplies a strong precedent for declared required dependencies and automatic installation. It does not establish the whole earlier recommendation: optional functional integrations, consumer version constraints, respecting deliberately disabled dependencies during installation, and preserving pins need our own explicit policy.

A small first implementation could declare required IDs, show the install plan, install missing dependencies, and identify unavailable requirements clearly. If we also introduce dependency version ranges, keep conflict behavior explicit rather than suggesting a full multi-version solver already follows from VS Code. Calls should retain the already accepted rule: disabled extensions are not silently re-enabled.
