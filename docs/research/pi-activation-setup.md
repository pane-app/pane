## Q15: Activation and background behavior

Pi loads the enabled extension set during resource initialization/reload. Its loader iterates the resolved extension paths, imports each module, and awaits its factory. Factories register commands, tools and event handlers. This is eager extension initialization, even though individual tool and command handlers run when invoked. It is not equivalent to a manifest-driven scheme that delays importing extension code until its first command is used. Sources: [extension loader](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/extensions/loader.ts), [resource loader](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/resource-loader.ts).

Pi's authoring contract tells authors not to start processes, sockets, watchers or timers in the factory: some invocations load extensions without opening a session. Long-lived work starts in `session_start`, or in the command/tool needing it. Authors release resources in an idempotent `session_shutdown` handler. Consequently, Pi supports background work through ordinary trusted extension code and lifecycle events; it does not make every installed extension a separate always-running process. Dynamic tool activation selects already registered tools, which should not be confused with lazy extension loading. Source: [extension lifecycle and tool documentation](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/docs/extensions.md).

Implication for our launcher: copying Pi's authoring convenience does not require copying eager initialization. Index declarative command metadata at startup and load implementation on first use, while supporting enabled startup listeners and background services. Lazy activation is now accepted for the launcher; it is an adaptation, not existing Pi behavior. Exact metadata and execution mechanisms remain implementation proposals.

## Q16: Runtime and toolchain setup

The documented npm installation of Pi requires Node.js 22.19 or later. The CLI README separately offers a macOS/Linux installer. Source: [CLI README](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/README.md).

Pi also builds standalone platform executables with `bun build --compile`, including Windows, macOS and Linux targets on x64 and ARM64. Those executables contain the JavaScript runtime; running this build is distinct from installing Pi through a system Node/npm installation. Packaging also includes assets and architecture-specific native helpers. Source: [binary build script](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/scripts/build-binaries.sh).

However, standalone runtime packaging does not remove all extension-install dependencies. The package manager's default package-manager command is external `npm`; settings can select another command, with explicit handling for pnpm/Bun. npm package installs invoke that command. Git packages invoke external `git clone`/checkout and run dependency installation when a `package.json` exists. These extension-install argument lists do not universally add `--ignore-scripts`. Therefore extension package scripts, native dependencies or external tools can add setup requirements. This is a source-derived consequence, not a claim that every package needs a compiler. Source: [package manager implementation](https://github.com/earendil-works/pi/blob/2b0a123de98318c2ff8069661721ce0c3794c34e/packages/coding-agent/src/core/package-manager.ts) (`getNpmCommand`, `getNpmInstallArgs`, `getGitDependencyInstallArgs`, `installNpm`, `installGit`).

Implication for our launcher: Pi-style npm/Git/local distribution alone does not ensure toolchain-free installation. A managed JS runtime and dependency installation path, plus prebuilt Rust artifacts per OS/architecture, can provide that normal-user experience. Source-only Rust packages or extensions requiring external programs may still declare additional prerequisites; developer toolchains remain necessary for authoring/building. This is a design recommendation, not a promise of compatibility with every npm package.
