# Fetch Git packages with Pane's own smart HTTP client, one checked revision at a time

Proposed 2026-09-29 by the implementation of #46; not yet confirmed by the user. ADR 0002 keeps Git as a distribution source and ADR 0012 identifies a Git package by its normalized host and repository path without its reference. The spec (US20, Q16) promises that a user installs a supported package without installing Git or a compiler; Windows and macOS do not ship a `git` program, and one the user installed runs the repository's and the user's configuration (hooks, `core.fsmonitor`, `core.sshCommand`, filters, `GIT_*` variables).

So Pane fetches a Git package itself, with a small client of Git's smart HTTP protocol, version 2, and no `git` program, library or configuration. Its requests go through Pane's one HTTP stack (ADR 0018, ADR 0019, `crates/pane-core/src/http.rs`, which gains a POST): `GET <repo>/info/refs?service=git-upload-pack` for the capabilities (protocol version 2 and SHA-1 object ids are required), `ls-refs` to resolve the reference, and `fetch` with `want <commit>`, `deepen 1` and `done`, for one pack holding exactly that commit and its tree. Pane reads the pack itself: its checksum, each entry's zlib stream within its declared size, offset and reference deltas, and every object's SHA-1 id, computed with collision detection (`sha1-checked`, as Git itself detects SHAttered-style collisions). The files written are the tree of the commit asked for, walked from that commit id, so pinning by commit id pins the bytes.

**What is taken.** Only regular files (written without execute permission) and folders. A symbolic link, a submodule, any other mode, a `.git` or `git~1` entry (in any case, and with the characters HFS+ ignores in a name, as Git's `is_hfs_dotgit` checks), two names in a folder that differ only in case, and every name npm's unpacking refuses (ADR 0019: `..`, a name longer than 255 bytes, `\ : < > " | ? *`, control characters, a trailing dot or space, Windows device names) refuse the whole revision on every system alike. A tree entry is one name, so the check refuses any entry that is not exactly one plain name: `/` anywhere (`a/b`, `../x`, an absolute `/path`, which `Path::join` would put in place of the download folder), `\`, `.`, `..` and whatever the system reads as more than one `Component::Normal`; such a tree is refused before anything outside its download folder can be written. The limits are 16 MiB for a reference listing (one longer is taken, for a commit named by its id, as naming no branch or tag that points to it: cautioned about, not refused), a 64 MiB pack, 20,000 objects, one budget of 256 MiB for the pack's contents in memory (its entries once inflated and the objects its deltas make, a delta's instructions let go once it is applied), 256 MiB of files, 10,000 files and folders, folders 32 deep and delta chains 4096 long. Deltas are resolved from a work list, each waiting on its base by entry or by id, so each is applied once, in time linear in the pack and without recursion. Text a server chooses (a commit subject, an `ERR` or failure message, a connection failure's text, a reference listing line, a `symref-target`, a tree entry's name) is shown without control characters, line separators or format characters (Unicode's Cf: bidirectional overrides and isolates, zero-width spaces and joiners, soft hyphens, tags), and cut to 200 characters, decoding at most 1 KiB of it. The revision is written into a download folder of its own under `extensions/downloads/`, shared with npm's (reference-counted with the packages read from it, removed once a preview is shown, an install ends or anything fails), and then read and installed as a local folder is: only `pane.json`, its components and this system's helper files reach the managed copy. Nothing is built, and nothing from the repository runs to install it (its components and helpers run only as the extension's own, once installed): a revision whose `pane.json` names a component it does not hold is explained as source-only, and one whose component is a Git LFS pointer as stored with LFS.

**Addresses and identity.** Only `https://` is fetched. `ssh://`, `git@host:path` and scheme-less `host/path` addresses are read as the same repository and fetched over HTTPS from the same host and path; credentials in an address, other schemes (`git://`, `file://`) and plain `http://` are refused, except `http://` to a loopback address written as one (`127.x.y.z`, `[::1]`, not `localhost`) in tests and development builds (`cfg(any(test, debug_assertions))`), which the tests and smokes serve. The preview says when an SSH address was fetched over HTTPS ("SSH address fetched over HTTPS from https://…"). The identity is `git:<host>[:port]/<path>`: the host in lowercase, HTTPS's port, a trailing `/` and `.git` dropped. **By the user's decision (2026-09-29)**, on github.com, gitlab.com, bitbucket.org and codeberg.org (on HTTPS's own port), which serve a repository at any case of its path, the path is lowercased too, and its `.git` dropped in any case, so `Owner/Repo` and `owner/repo` are one package there (#46 AC2); every other host keeps the path's case, since a server may tell them apart. The address is fetched as written, whatever the identity. No redirect is followed, no credentials are sent (a repository asking to sign in is explained), no proxy is used, and the User-Agent is `git/pane-<version>`, as Git hosts serve the smart protocol to `git/` agents.

**References.** `@<reference>` after the address names a branch, a tag (both refused as ambiguous, unless written `refs/heads/…` or `refs/tags/…`) or a full commit id; none is the default branch. A branch (and the default branch) is **tracked**: an update fetches it again. A tag or a commit is **pinned**: an update without a reference keeps it; naming another reference changes it. `installed.json` records `gitUrl`, `gitRef` (`refs/heads/…` or `refs/tags/…`), `gitCommit` and `pinned`. A dependency's `git:` source may name a reference, which the one installed copy must be at, or the install stops with a conflict (as #45's npm pins).

**A commit id pins contents, not provenance.** Fetching `owner/repo@<commit id>` proves that the files are that commit's tree, not that `owner/repo` made the commit: a host that shares object storage between forks, as GitHub does, serves a commit that exists only in a fork or a pull request at the upstream repository's address too, so `trusted/repo@<id>` can install code the repository's owners never merged. Pane cannot tell from the server where a commit came from. So when a commit is named by its id, by the user or by a dependency's `git:` source, Pane also lists the repository's `HEAD`, branches and tags (`ls-refs`, peeled), and the preview adds a caution when none of them points to that commit, for a dependency on the line after its "Requires:" ("Caution: no branch or tag of github.com/owner/repo points to commit 1a2b3c4d5e6f. A host that shares storage between forks, as GitHub does, can serve a fork's or a pull request's commit at this address, so its id alone does not show that this repository made it"). A commit an advertised reference points to is still only as trustworthy as that reference. The preview's "Fetched:" line says where the commit was served ("served at https://…"), not where it came from. A branch or tag is resolved from the repository's own listing, so this applies to commit ids only.

Rejected: running a `git` program (a manual setup on Windows and macOS, and hooks, filters, `core.fsmonitor`, `core.sshCommand`, `uploadpack`/`protocol.allow` settings and `GIT_*` variables to neutralize, which Pane would have to track as Git changes); libgit2 (C code, OpenSSL, and the same configuration surface); gitoxide (`gix`: a large dependency tree whose fetch needs its own HTTP backend, reqwest or curl, a second HTTP stack beside ADR 0019's, and whose checkout applies filters and writes links we would have to turn off); host-specific archives such as GitHub's `codeload` tarballs (one host's API, not Git, and no commit-id check of the files); protocol versions 0 and 1 (every major host serves version 2); full clones (history the install never uses); submodules and Git LFS (other repositories and servers, fetched with other trust).

Still open: SSH transport and private repositories with credentials; proxies; SHA-256 repositories; servers that refuse `deepen` or unadvertised commit ids (GitHub, GitLab and Git's own server allow both); a package in a subfolder of a repository; automatic updates of tracked branches (#50); signed tags or commits. No check reaches a real Git host: the tests and smokes make repositories with `git` and serve them from 127.0.0.1 with `git upload-pack`, and [trying a real host by hand](../git.md#trying-a-real-host-by-hand) is documented and not run.
