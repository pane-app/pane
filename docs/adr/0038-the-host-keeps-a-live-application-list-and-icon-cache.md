# The host keeps a live application list and an icon cache

Accepted 2026-10-06 by the user's decision on the scope of the applications specification, after the [Raycast deep dive](../research/raycast-deep-dive.md#windows-integration): applications get a stable identity, real icons and a list that stays current by itself. It amends [ADR 0015](0015-host-finds-and-opens-applications-for-an-extension.md), whose host adapter "holds no state of its own", and replaces the 10-second rescan of today's cached list ([applications](../applications.md#behavior)). The rest of ADR 0015 stands. The host still finds and opens applications through `pane:extension/applications`, with one adapter per system. The Applications default extension still supplies them to root search as indexed results, and disabling it still stops all looking for applications. Nothing moves into the core, and no native helper is used.

So the host keeps three things while an application list is needed.

**A live list, by identity.** Each application has an opaque id that the host gives it: a digest of a typed key, the same on every start and on every machine with the same installation. On Windows the key of a desktop program is the shortcut's resolved target and arguments, with version folders (such as `app-1.2.3`) replaced by a wildcard, and the key of a packaged app is its package family. On macOS the key is the bundle identifier, and on Linux the desktop file id. The host keeps the map from each id to the source it opens, so `open(id)` works whatever the id looks like, and an id that was a path before this change still resolves. Several sources with one key are one application, and the host chooses which of them names it and opens it.

**Watchers that keep it current.** On Windows the host watches the shortcut folders, debouncing changes by about half a second, and follows the system's packaged-app events. On macOS it watches the application folders with FSEvents, and on Linux the `applications` data folders with inotify. An application whose last source disappears stays listed for five seconds and is removed only if nothing with its identity came back meanwhile, so an update that uninstalls and reinstalls never makes it flicker out of search. An overflowing watcher, a resume from sleep and a periodic check trigger a full rescan, which replaces the list by identity. A failed rescan keeps the list, as today. When the list changes, the launcher asks every enabled command with indexed results that imports the applications interface for its results again: at once if root search is on screen, otherwise at the next visit. No guest export is added for this, because the guest reads the host's current list, which answers at once.

**An icon cache.** The host extracts each application's own icon at 256 pixels. It rejects an icon padded into a larger canvas and keeps a packaged app's light and dark variants. It caches them in Pane's cache folder, keyed by id and by a fingerprint of the source. The cache is Pane's own, never extension data or a managed copy. It is written atomically, an unreadable one is deleted and rebuilt, and deleting it loses nothing but the time to extract again. After each start, a worker at low priority refreshes every icon in the background, rows on screen first. Extraction never runs on the window's thread or the extension runtime's thread. The host returns an icon reference with each application, so any extension can show it. Root search draws it bare, as [ADR 0035](0035-the-launcher-borrows-raycasts-polish-within-the-accepted-ui.md) decides.

The state lasts only while it is needed. The list is built and the watchers start when an enabled, running package first asks for the installed applications. Both are dropped when no package that asked can run any more: its generation ended through a disable, an uninstall, a pause or a code replacement. So [ADR 0005](0005-lazy-activation-and-managed-dependencies.md)'s lazy activation holds: nothing watches for applications while no package uses them. The icon cache stays on disk between runs, as a cache does. The applications specification sets the exact bounds, timings and rescan period.

ADR 0015 kept no state because its first slice needed none. A list read again on demand had no identity beyond a path, and a stateless adapter was the smallest thing that worked. Three later choices need state. Root search's learning ([ADR 0030](0030-root-search-learns-from-what-the-user-chooses.md)) and quick slots ([ADR 0026](0026-host-keeps-quick-slots-by-identity.md)) key an application by its id, so the id must survive an update that moves the program to a new version folder, as Discord and Slack do. Bare application icons need icons, and extracting them is too slow to repeat for every query: Raycast's first extraction of about 125 icons took about 7 seconds in the background. A list that stays current needs watchers, and someone must own them. Today an application installed while Pane is open appears only from the second return to root search after it. Raycast for Windows keeps exactly this state: identity by resolved target with version folders wildcarded, a binary icon cache refreshed after each start, folder watchers debounced by half a second, package events and a five-second grace before removal. The host owns the state because the guest cannot watch folders or extract icons. One list, kept once, also serves every extension that imports the interface.
