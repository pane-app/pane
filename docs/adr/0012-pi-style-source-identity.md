# Identify extension packages by their source

Accepted in Q29: after comparing Pi, Raycast, VS Code and generated UUIDs, the user chose "ok do like pi". Use Pi-style source-derived package identity: npm package name without its version, normalized Git host/repository path without its ref, or resolved absolute local path. This fits open npm/Git/local distribution without requiring a launcher-owned publisher registry or author-generated UUID; readable titles remain separate.

Equivalent source declarations identify the same package, while npm, Git and local copies can be distinct even when they contain the same code. Keep Q28's explicit duplicate-install rejection for the same canonical identity and ordinary updates to the tracked installation; do not adopt Pi's personal/project precedence as an unstated launcher feature. Renamed/moved sources may change identity, and automatic source/data merging remains unselected. Package identity is distinct from resource/operation addressing: exact multi-resource packaging and dependency target syntax remain open. Q30 subsequently selects manual developer control of local versus published copies, without automatic switching or restoration. See [source comparison](../research/extension-identity.md) and [Pi audit](../research/pi-extension-identity.md).

**Amended 2026-10-08 by [ADR 0044](0044-a-git-repository-holds-one-extension-or-a-collection.md):** an extension in a collection is identified by its repository and the id the collection gives it, `git:<host>/<path>#<id>`, not by its folder, so moving its folder, or renaming its id through the collection's `renamed` map, keeps its identity. A one-extension repository keeps `git:<host>/<path>`, and one npm package remains one extension.
