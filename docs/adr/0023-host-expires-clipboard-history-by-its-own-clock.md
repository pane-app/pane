# Pane expires clipboard history itself, before anything reads it

Proposed 2026-09-29 by the implementation of #36; not yet confirmed by the user. Clipboard history must have a finite, configurable retention that keeps running while the extension is disabled or uninstalled with its data kept and while Pane is stopped, so that re-enabling never revives expired items (US67, US68; T10, T21; G5). [ADR 0020](0020-host-keeps-clipboard-history-for-an-extension.md) made the history the package's extension data, written by the host.

So the host expires it too, without running the extension. Each item keeps the time it was copied, and each package's history its retention (`retentionSeconds` in `clipboard-history.json`, absent for the default), so an item's deadline is fixed when it is copied: disabling, re-enabling or a restart never moves it, and changing the retention applies to the kept items at once. Every read, count and change of the history first removes the expired items of every package, and writes the file without them, so nothing expired is ever shown, counted in an uninstall or retained-data row, copied again or kept by a later write, however long Pane was stopped. While Pane runs, a thread of its own also removes them when they expire (and looks again at least hourly, for a changed system time), so the file does not hold them longer than Pane runs idle. Tests and development builds can give the launcher a clock of their own (`Launcher::with_clock`); release builds always use the system's.

Deleting (one item, several, Clear, turning history off and deleting it, uninstall's delete) counts as a deletion, so a clipboard read already in progress keeps nothing afterwards (ADR 0020's fence); expiry does not, since what a read keeps was copied after what expired. Turning history off and deleting it is one change, so no copy is kept between the two. None of it is forensic erasure, and none of it changes what is on the system's clipboard.

Asking the extension to expire its own items was not used: it may be disabled, uninstalled or never run (on macOS and Linux it is unavailable). Expiring only on a timer was not used either: after downtime the file holds expired items until the timer runs, and a read could come first. Keeping deadlines instead of copy times was not used, since the retention would then apply only to later items.

The default retention, 7 days, and the offered choices (1 hour, 1 day, 7, 30 or 90 days; the host accepts 1 minute to 365 days) are provisional, pending the user's decision ([current decisions](../current-decisions.md)).
