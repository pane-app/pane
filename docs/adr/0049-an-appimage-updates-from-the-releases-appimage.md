# An AppImage updates from the release's AppImage

Accepted 2026-10-23 with [#464](https://github.com/pane-app/pane/issues/464), the user's choice that Pane installs like a normal application on every system: a disk image on macOS and an AppImage on Linux, beside the zip and the tarball ([spec #451](https://github.com/pane-app/pane/issues/451)). It extends [ADR 0048](0048-pane-updates-itself-from-github-releases.md), whose check, download, checksum and redirect rules stand.

ADR 0048 gave a release one package per system, and made those asset names the contract between the packaging task and the updater. The installers add two assets to a release: `Pane-<version>.dmg` and `Pane-<version>-<arch>.AppImage`, each with its `.sha256` beside it. The question is which asset a Pane installed from each one updates from.

**macOS keeps the zip.** A `Pane.app` dragged out of the disk image is the bundle the zip's install script builds: same layout, same `Info.plist`, same program. An update replaces `Contents/MacOS/pane` with the program the zip holds and rewrites the plist's version ([#455](https://github.com/pane-app/pane/issues/455)). That works wherever the user put the bundle: `/Applications`, `~/Applications`, anywhere they can write. Reading the dmg would mean mounting it with `hdiutil` and copying a whole bundle under a running Pane, which the zip already avoids.

**An AppImage updates from the AppImage.** A Pane running from an AppImage runs a program inside a read-only mount, which is gone once Pane exits. The file the user keeps is the AppImage, and that is what an update must replace. Such a Pane takes the release's `Pane-<version>-<arch>.AppImage` and its `.sha256`, and passes over a release that carries no AppImage, as it passes over one that has no package for its system. The swap is the same as any other update: the new file is staged beside the old one, the running AppImage is renamed `<name>.old` and the new one takes its path. The menu entry, autostart entry and desktop shortcuts that name that path keep working. The file keeps its name even when the name carries the old version. Before anything is replaced, the download must be an ELF file with the AppImage type 2 mark. The staging folder is hidden and named after the AppImage (`.<name>.update`), because an AppImage usually sits in a folder of the user's own, where a folder named `update` may well be theirs.

**How Pane knows.** The AppImage runtime sets `APPIMAGE` (the file) and `APPDIR` (the mount) for the program it starts. Pane counts as an AppImage only when its own program is inside `APPDIR` and `APPIMAGE` is an absolute path to a file. A program that only inherited the variables from another AppImage does not count. Pane reads them once, as it starts, then takes them and the runtime's `ARGV0` and `OWD` out of its environment. Otherwise every program Pane starts would inherit them and think it runs from Pane's AppImage. An Electron app's updater, for one, reads `APPIMAGE`. The autostart entry names the AppImage file for the same reason.

**A tarball install is unchanged.** A program the tarball's install script put in `~/.local/bin` still updates from the tarball.

**Rejected.**
- Updating an AppImage from the tarball: it would put a bare program where the AppImage was, losing its desktop entry and icons. It would also be a different kind of file under the AppImage's name.
- AppImage's own delta updates (zsync and `AppImageUpdate`): they need update information embedded in the file and a tool Pane does not ship. Pane's own updater already checks, asks and verifies.
- Renaming the AppImage to the new version: that would break every entry that names the old path.

**Consequences.** `cargo xtask package-macos` also builds the disk image (`hdiutil`, which every Mac has). `cargo xtask package-linux` also builds the AppImage when `APPIMAGETOOL` and `APPIMAGE_RUNTIME` name the tools. CI's Package job downloads them pinned and checks their digests. The release draft refuses a release that lacks either installer. On Linux the swap needs the AppImage's folder to be writable by the user; one in a root-owned folder is explained, not worked around. A disk image is not the same bytes wherever it is built, and neither is an AppImage, unlike the zip and the tarball. The `.sha256` beside each says what was built.
