# Download npm packages with Pane's own client, checked and unpacked without scripts

Proposed 2026-09-29 by the implementation of #45, revised the same day after its review; not yet confirmed by the user. ADR 0002 keeps npm as a distribution source and ADR 0012 identifies a package from npm by its name without version. The spec (US20, Q16) promises that a user installs a supported package without installing Node, npm or a compiler, while ADR 0008's managed Node is no longer the baseline: a Pane extension is WASI 0.3 components (ADR 0013), not Node code.

So Pane fetches an npm package itself rather than running npm or a managed Node. It reads the registry's abbreviated metadata for the name, takes the exact version asked for (which pins it) or else the `latest` tag (ranges and other tags are refused), downloads that version's tarball over HTTPS only from the registry's own scheme, host and port, following no redirect, and requires the registry's sha512 `dist.integrity` to match (a version with only a sha1 `shasum` is refused). The unpacked `package.json` must name the package and version asked for. The package is then read, checked and installed as a local package is (#9, #15), copying only `pane.json`, the components it names and this system's helper files, while it keeps its npm identity.

**Unpacking.** The tarball is read entry by entry as written, extension headers included, so that Pane rather than the tar reader decides what they mean: a GNU long name or a PAX `path` names the next entry and is checked like any other name; a PAX `size` must equal the entry's own header size (two readers must never see different files in one tarball); each extension header is at most 64 KiB and counts toward the limits; long link names, global headers that change paths or sizes, and headers describing no entry are refused. Only regular files and folders are taken, each inside the package, without its top folder and without execute permission. The same names are refused on every system, so a tarball one system unpacks, every system unpacks: absolute paths, `..`, empty or `.` parts, a name longer than 255 bytes (checked before the rest of it is read), `\ : < > " | ? *`, control characters, a trailing dot or space, and Windows device names (`con`, `prn`, `aux`, `nul`, `conin$`, `conout$`, `com0`–`com9` and `lpt0`–`lpt9` with a digit or a superscript `¹ ² ³`, whatever follows a dot), compared by character. The limits are 16 MiB of metadata, a 64 MiB tarball, 256 MiB unpacked and 10,000 entries; anything else refuses the whole tarball.

**Downloads.** Each download is unpacked into a folder of its own under the data folder's `extensions/downloads/`, named by when it was begun, the process and a count, and is removed when the last package read from it is dropped: once a preview is shown (its dependencies' downloads too), once an install ends, and on every failure, a component failing its check included. No two previews or installs share a folder. A starting Pane removes only downloads begun more than a day ago, so another Pane's install in progress on the same data folder survives.

**Pins.** Naming a version pins the package to it (`installed.json` records `npmVersion` and `pinned`). Updating a pinned package without naming a version keeps its pin; naming another version changes it. A dependency's `npm:x@1.2.3` must get that version: an installed `x` of another version, another dependent pinning another one, or the latest taken for a dependent that pins none is a conflict the plan explains, as #42's other conflicts are, and nothing is installed.

**The client.** npm's two requests (metadata, tarball) go through the same code as guests' web requests (ADR 0018, `crates/pane-core/src/http.rs`): hyper over HTTP/1.1, TLS with rustls and the ring provider, trusting the system's certificates through rustls-native-certs, on a runtime of the download's own worker thread, with a new connection per request, no proxy and no redirect. One HTTP stack serves the whole host; its certificate trust is the same for an extension's request and for Pane's own. `tar` and `flate2` unpack and `sha2` checks the integrity. The registry is `https://registry.npmjs.org/`, and release builds have no way to replace it. In tests and development builds only (`#[cfg(any(test, debug_assertions))]`), `Launcher::with_npm_registry` and `PANE_NPM_REGISTRY` name a registry that must be a loopback address written as one (`127.x.y.z` or `[::1]`, which may be plain HTTP; `localhost` is refused, since a name could resolve elsewhere); the tests and smokes serve one from fixtures, so no check reaches the network.

Nothing in the package runs to install it. npm's lifecycle scripts (`preinstall`, `install`, `postinstall`, `prepare`…) are never run and the package's own npm dependencies are never installed; the preview says so, and names the scripts and dependencies its `package.json` declares. A tarball without `pane.json` is an ordinary npm package, which Pane explains it does not run; one whose `pane.json` names a component the tarball lacks is a source-only package its author must build before publishing. There is no build step for npm packages.

Rejected: running npm or a managed Node (a runtime the user would need, and install scripts Pane would run); following the tarball URL to another host (a mirror would have to be trusted separately); a registry setting for users (enterprise registries, scoped registries and credentials are later work); a second HTTP client for Pane's own requests (first `ureq` with `rustls-platform-verifier`: two stacks would trust certificates differently); letting the tar reader apply extension headers (it reads each one whole, with no limit of its own, and a size only its header gives would be read differently by another reader); sharing one unpacked folder between downloads of one tarball (a removal could delete what another preview reads); removing every download when Pane starts (another Pane's install would lose its files); silently installing or keeping a version a dependency did not pin, or unpinning on an update.

Still open: private and scoped registries and their credentials, `.npmrc`, proxies (none is used, as for guests' requests), resuming or caching downloads across starts, signatures and provenance beyond the registry's integrity, automatic updates of unpinned packages (Q21), a way to unpin other than reinstalling, and a Git source (`SourceSpec` has room for one). No check reaches the real registry; [trying it by hand](../npm.md#trying-the-real-registry-by-hand) is documented and not run.
