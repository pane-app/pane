# Let the host find and open applications for the Applications extension

Proposed 2026-09-28 by the implementation of #24, #25 and #26; not yet confirmed by the user. App launching is a disableable default extension ([ADR 0001](0001-small-core.md), spec constraint 1), and the core owns matching, ranking and dispatch ([ADR 0006](0006-raycast-style-search-with-extension-providers.md)). A WASI 0.3 guest cannot list the system's application folders or start a program, so something native must.

The host provides that as an extension API, `pane:extension/applications` (list installed applications, open one), with one adapter per system: Start menu shortcuts on Windows, application bundles on macOS, XDG desktop entries on Linux. The Applications extension, a Rust component, uses it and supplies the applications to root search as indexed results (results given ahead of the query, which the core keeps, matches and ranks by title, and whose `open-application` action the core performs). Disabling the extension removes its results and stops all looking for applications; the host adapter holds no state of its own.

A native helper ([ADR 0014](0014-optional-native-extension-helpers.md), #15) was not used: the host already runs natively on each system, listing folders and asking the system to open a file needs no library the host lacks, and a per-OS helper binary would add packaging and a managed process for nothing. Putting the whole feature in the core was not used either, since it must be disableable as an extension. Windows' packaged apps are listed through the shell's COM interfaces from the host too, since the host already links the Windows crates; a later integration needing libraries the host lacks may still be a helper.
