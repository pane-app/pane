# Extensions get the user's attention through a system notification, a ringing sound and the launcher

Proposed 2026-10-26 by [#554](https://github.com/pane-app/pane/issues/554), after the user's direction of the same day on spec [#553](https://github.com/pane-app/pane/issues/553): a small host capability, not PowerShell from each extension. Where Raycast has a precedent it is followed (the user's standing rule, "do like Raycast"); where it has none, this says what was chosen and why. Not yet confirmed by the user.

**Why.** An alarm, a timer, a Pomodoro or a reminder registers an owned timer ([ADR 0041](0041-extensions-compose-through-capabilities-that-pane-brokers.md)) and is called when it fires, usually while Pane's window is hidden. It then has no reliable way to tell the user:

- `show-hud` closes the launcher and shows a message for 1.2 seconds (3 for a failure), too brief to notice from across the room.
- `show-toast` lives in the launcher's footer and is shown as a HUD while the window is hidden; `confirm` needs a window shown for the call and answers "not available" in a call with none, such as a timer's firing.
- A system program ([ADR 0033](0033-extensions-may-run-system-programs.md)) could post a notification or play a sound through PowerShell or `osascript`, but only inside the call that started it, and with exactly the fragility Raycast's Timers extension shows: its changelog is full of fixes for notifications that need Script Editor allowed in Focus settings, sounds that did not play when the notification failed, and leftover files.

Raycast's own API gives extensions a HUD and a toast and no system notification, so its extensions shell out. Pane's host already does what a WASI 0.3 guest cannot for applications ([ADR 0015](0015-host-finds-and-opens-applications-for-an-extension.md)), a granted folder ([ADR 0017](0017-host-lists-a-granted-folder-for-an-extension.md)) and clipboard history ([ADR 0020](0020-host-keeps-clipboard-history-for-an-extension.md)); this is one more such capability.

**How it sits with the small core ([ADR 0001](0001-small-core.md)).** The core gains no alarm, timer or clock: those stay extensions (the clock extension gets its own specification). It gains two small host functions any extension may use — a **system notification** and a **ringing sound** — in a new interface, `pane:extension/alerts` ([wit/alerts.wit](../../wit/alerts.wit)), imported only by a component that calls it, as the open windows' and the typed folder's are. Showing the launcher needs no new function at all (below). Each system adds an adapter; until it has one, the calls answer an explained "not available".

## The system notification

`notify(notification)` posts a notification through the system's own notification service — Windows' toast notifications (WinRT `ToastNotificationManager`, through the `windows` crate Pane already uses), later macOS's user notifications and the freedesktop notification service on Linux ([#559](https://github.com/pane-app/pane/issues/559)) — from any call, with no window needed.

- **Its shape:** a title, an optional message, and an optional click. Plain text, no markup or images. A title over 200 characters or a message over 1,000 is cut with "…" rather than refused: the system cuts shorter anyway, and an alarm should never fail over its wording. Pane adds the package's title as the notification's attribution (Windows' attribution line), so the user can tell which extension spoke; the notification itself is Pane's, under Pane's name and icon.
- **A click launches one of the calling package's own commands**, with the context the extension gave, exactly as `launch` from `wit/commands.wit` launches it user-initiated, under the rules for showing the launcher below. That makes a "Timer done" notification open the timer's screen, which is what users expect from a notification. Only the caller's own commands: the notification speaks for its package. A notification without a click, or a click the system does not deliver to the running Pane, shows the launcher as a second start does ([ADR 0052](0052-a-second-start-shows-the-running-pane-and-exits.md)), where the system starts Pane's program for it. No action buttons: they are where the platforms differ most, and the launcher's own screen (below) does Snooze and Dismiss better.
- **It is silent.** Pane asks the system to play no sound with it. A sound is the ringing sound's job, so one alert never plays two sounds at once, and an extension that wants a short chime rings once.
- **The answer** is that the system took the notification, not that the user saw it. `not-available` says why it could not be posted at all: no adapter on this system yet, the user turned notifications off for Pane or for the system (Windows' `ToastNotifier.Setting` says so), or Windows has no AppUserModelID for this Pane. It is never silent and never a crash.
- **AppUserModelID on Windows.** A toast from an unpackaged Win32 program shows only if the program has an AppUserModelID Windows knows. Pane uses one fixed id, `PaneApp.Pane`, set on its own process (`SetCurrentProcessExplicitAppUserModelID`) and carried by the Start menu shortcut the setup creates ([installer](../installer.md)). A portable Pane and a development build have no such shortcut; Pane then registers the id for the user under `HKCU\Software\Classes\AppUserModelId\PaneApp.Pane` (its display name and icon), the documented way for an unpackaged program without a shortcut. A debug build uses `PaneApp.Pane.Development`, so it never takes over the installed Pane's notifications. [#555](https://github.com/pane-app/pane/issues/555) checks what each of the three actually does on Windows 11 and records it; whatever cannot show answers `not-available` saying why.

## The ringing sound

`ring(sound, repeat, volume)` starts a sound and answers a **`ringing`** resource the extension owns ([ADR 0041](0041-extensions-compose-through-capabilities-that-pane-brokers.md)): an owned registration, on the generation's undo list as a timer is. Raycast has no sound API either; its Timers extension ships sound files, lets the user pick one and its volume, and can "ring continuously" by looping `afplay`. This gives an extension the same choices without a process per sound.

- **Which sounds.** Three bundled with Pane — `alarm` (insistent, for alarms), `bell` and `chime` (gentle, for reminders) — as short WAV files made for Pane or under CC0, checked against [licensing](../licensing.md) by [#556](https://github.com/pane-app/pane/issues/556), so every extension sounds right on every system without shipping audio; `system`, the sound the system's own sound scheme plays for notifications, so an extension can match what the user chose; and `file`, a WAV or MP3 file the extension names, absolute or relative to its package's folder (so a package can ship its own sound), at most 10 MiB. Two formats keep every system's decoder small; WAV and MP3 cover what authors have.
- **Repeat:** `once`, `times(n)` (n from 1 to 100) or `until-stopped`, back to back with no gap beyond the sound's own silence. Every ringing stops by itself after **10 minutes**, however it was asked, so a bug, or an alarm nobody is there to hear, cannot ring all day; an extension that really wants more rings again.
- **Volume:** 0 to 100, a percentage of the sound's full level at the output's own volume. Pane never changes the system's volume or unmutes it.
- **Stopping it is dropping the handle.** There is no `stop`: as for every owned registration, dropping the handle stops the sound at once, and so does the instance holding it going away (a crash, a stopped call, an unresponsive stop) and the generation ending (a disable, a pause, a reload, an update, an uninstall, Pane quitting). A disabled or crashed extension never rings forever, and the author writes no cleanup. Dropping one that already finished does nothing. The handle lives in the instance that rang, so the command that stops it (a "Ringing" screen's Dismiss) is served by the same component and keeps the handle in its state, as the sample of [#558](https://github.com/pane-app/pane/issues/558) does.
- **Never in the way.** Audio runs on a thread of Pane's own; neither the window nor the runtime ever waits for it. On Windows, WASAPI in shared mode through the `windows` crate Pane already uses (its `Win32_Media_Audio` feature is on), with Media Foundation decoding the file: no new audio crate, and nothing every Windows lacks. macOS and Linux choose theirs in #559, with no assumption of one sound server on Linux. Tests use a stand-in sink, so they make no noise and can check that each way of ending the code stops the sound.
- **The answer.** `not-available` when this system has no adapter yet or there is no output device; `failed` when the file cannot be read or decoded; a muted device plays silently and answers success, since Pane cannot tell muted from quiet and should not care. A device removed mid-ring ends the sound and is written to the package's extension log. None of it is a reason to pause the extension.

## Showing the launcher on the extension's command

There is no new call. An extension shows the launcher on one of its commands from a call with no window — a timer's firing, a schedule, a service, the activation entry point — with **`launch`** of `wit/commands.wit`, **user-initiated**, naming its own command and passing context. This is Raycast's precedent: `launchCommand({ name, type: LaunchType.UserInitiated, context })` from a background command brings up Raycast's window on that command. Pane already does it — a user-initiated launch of a view command shows the window for it from any call (`Launcher::take_window_request`) — so the gap is not a missing call but missing rules for when the user did not just ask for Pane. [#557](https://github.com/pane-app/pane/issues/557) adds them, for a user-initiated launch asked from a call no window was shown for (an **attention launch**):

- **The launch record** is what any launch by a command carries: `user-initiated` (the user will act on the screen), source `command`, the command's id, and the context the extension passed (JSON text, at most 1 MiB). The extension recognises its own context; `launch-type` and `launch-source` gain no case, since changing a type every command imports would change the shape every extension is built against.
- **Hidden launcher:** it is shown on the command and takes the keyboard focus, so Enter and Escape act on the opened view at once, as when its hotkey opens it.
- **The user typing in another application:** Pane waits until the keyboard and the pointer have been still for 1 second, at most 10 seconds, so keys meant for a document never land in the launcher and Enter never dismisses an alarm by accident. The notification and the sound are not delayed, so the user is alerted meanwhile.
- **Launcher already open on another screen:** that screen makes way, as for any user-initiated launch (Raycast's behaviour), except while the user is typing in it (the same 1-second wait) or an **Alert** is pending there, which the launch waits for until it is answered. Settings stays open; the launcher is shown beside it as the Open Pane hotkey shows it.
- **Game mode with Pane's hotkeys paused** (a game in front): the launcher is not shown over the game. The launch waits until the game leaves the front, as the hotkeys do; the notification and the sound still go, so the user still hears the alarm.
- **Two at once:** attention launches queue in the order asked, one shown at a time, the next once the user leaves the one shown (back to root search, or the window hidden). One never takes another's screen. Each package holds at most one waiting attention launch; a newer one replaces its older one, so the queue is bounded by the packages installed.
- **What `launch` answers** is unchanged but for the own-commands rule below: success once the launch is accepted (now: queued), not when it is shown, and the same refusals — a command that is disabled, paused, waiting, unavailable or not a view. A waiting launch is dropped, never shown, when its package's generation ends.
- **Focus:** only an attention launch takes the focus. A notification, a sound, a toast, a HUD or a background launch never takes it from the user's application.

An attention launch may name only the calling package's own commands (the user's direction in [#557](https://github.com/pane-app/pane/issues/557)): `launch` asked from a call no window was shown for, user-initiated, for another package's command answers a refusal saying so. A launch that takes the focus while the user is busy elsewhere speaks for its package, as the notification's click does, so one extension can never push another's screen in front of the user. A user-initiated launch of another package's command from a call that has a window, the user's own action, stays allowed, as today and as Raycast's `launchCommand` allows it, and a background launch of any command is unchanged.

## Limits

- At most **2 ringing sounds at once per package** and **8 in all**; one more answers `limit`. Two let an alarm overlap a reminder; eight keep a misbehaving set of extensions from making a din.
- At most **10 notifications per package per minute**; one more answers `limit`. The system throttles too, but a bug in a 1-second timer should be refused by Pane, not by Windows.
- A ringing stops by itself after 10 minutes (above). A waiting attention launch is at most one per package (above).
- An unavailable platform answers `not-available` with a reason for the user, as `system-error` does; never a trap and never a reason to pause.

## Do Not Disturb, Focus assist and Game mode

Pane does not second-guess the system. Under Windows' Focus assist or Do Not Disturb, the system keeps a notification silent in the notification center; `notify` still answers success, since the notification was posted. The extension cannot learn whether the user saw it — Windows has no public way to read Focus assist's state — and does not need to: the sound and the launcher are its louder means. The ringing sound is not suppressed by Do Not Disturb, which silences notifications, not applications' audio, and an alarm the user set is something they asked to hear. Game mode holds only the launcher (above). Turning notifications off for Pane is the user's explicit choice, and `notify` answers `not-available` saying so.

## The WIT and the version

`wit/alerts.wit` holds the interface `alerts` (`notify`, `ring`, the `ringing` resource and their types) and the worlds `alerts-user` (the import alone, for guest bindings) and `extension-with-alerts` (the world Pane hosts, including `extension-with-typed-folder`). Adding an interface and a world is additive ([ADR 0046](0046-every-breaking-change-to-the-extension-api-gets-a-new-version.md)): an extension built for 0.2 keeps loading and working, so the extension API stays `pane:extension@0.2.0` and `docs/breaking-changes.md` gains nothing. The WIT guard agrees: it counts an added interface or world as not breaking. Until #555 and #556 land, Pane's host links the interface with stubs that answer `not-available` on every system.

**Rejected.**

- **PowerShell or `osascript` from each extension** ([ADR 0033](0033-extensions-may-run-system-programs.md)): the fragility Raycast's Timers extension shows, a process per alert, nothing that stops when the extension does.
- **A longer HUD, or toasts that outlive the window:** a HUD that stays is a window Pane would have to invent dismissal for, and still makes no sound; the system's notification center already keeps what the user missed.
- **A new call to show the launcher** (`show-command`): `launch` user-initiated already is that call, in Raycast and in Pane; a second call would split one behaviour into two.
- **A `stop` function on the ringing sound:** dropping the handle is how every owned registration ends (ADR 0041); a second way would invite handles kept alive after "stopping".
- **Ringing without an end:** an unattended alarm would ring until someone came home.
- **A new extension API version:** nothing an existing extension uses changes.

**Consequences.**

- The glossary adds **System notification**, **Ringing sound** and **Attention launch**, and says that an **Alert** is not the `alerts` interface.
- [#555](https://github.com/pane-app/pane/issues/555) implements `notify` on Windows (WinRT toast, the AppUserModelID above, a stand-in notifier for tests); [#556](https://github.com/pane-app/pane/issues/556) the ringing sound on Windows (owned registration, a stand-in sink for tests, the limits); [#557](https://github.com/pane-app/pane/issues/557) the attention launch's rules in `pane-core` and `pane`, and `launch`'s comment in `wit/commands.wit` saying them; [#558](https://github.com/pane-app/pane/issues/558) the Rust and JS/TS bindings (`pane_extension::alerts`, `pane:extension/alerts@0.2.0`, a `"pane": { "alerts": true }` option, `wit/alerts.wit` added to the WIT the JavaScript build embeds and the prebuilt samples' digests, which rebuilds them), a sample and the alerts page of the documentation; [#559](https://github.com/pane-app/pane/issues/559) macOS and Linux.
- Notifications that arrive while Pane is not running stay out of scope: alarms fire only while Pane runs, which starts at sign-in and lives in the tray.
