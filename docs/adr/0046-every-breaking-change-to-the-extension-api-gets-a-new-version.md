# Every breaking change to the extension API gets a new version, and Pane runs the previous one for a while

Accepted 2026-10-08 by the user's decision, after comparing how Pi handles breaking changes: Pi has no API version and no compatibility check when an extension loads, and about 52 of its 288 releases changed its extension API incompatibly, some in patch releases, so a broken extension usually loads and fails only when a changed call is made. The rule is accepted; the length of the support window and the adapter mechanism are *proposed* and were delegated.

[ADR 0010](0010-best-effort-extension-api-compatibility.md) favours stability without promising it, and left versioning, deprecation periods and migration open. Meanwhile API 0.1 changed shape between slices without a new number (#19, #21, #29, #170): Pane caught each stale build by type-checking the component before running it ("built for an older extension API shape"), and every affected extension was rebuilt in the same change. That worked while every extension lived in Pane's repository. With official extensions in repositories of their own ([ADR 0045](0045-official-extensions-live-in-their-own-repositories.md)) and collections from anyone ([ADR 0044](0044-a-git-repository-holds-one-extension-or-a-collection.md)), a silent shape change breaks extensions nobody can rebuild in the same change.

**The version.** The extension API version is the version of Pane's WIT package (`pane:extension@0.1.0`), and a manifest's `apiVersion` names the version an extension was built for. A change after which an extension built for the current version would fail to load, or would behave differently, is breaking and gets a new version: the minor before 1.0 (0.1 to 0.2), the major from 1.0. An addition that existing extensions keep working with needs no new version before 1.0 and a minor from 1.0. No change of shape ships under a version number that has already shipped.

**The previous version keeps working for a while.** Pane runs extensions built for its current API version and for the one before it, adapting the previous one in the host (*proposed*: the component model lets the host link both worlds). An extension built for the previous version is marked as such on its page, with what its author needs to do. Support for a previous version ends with the first Pane release after the one that replaced it (*proposed*), so authors get at least one release cycle.

**An unsupported extension is explained, not dropped.** An extension built for a version Pane no longer or not yet supports is refused before any of its code runs, stays listed, and says which version it needs, which this Pane provides, and whether to update the extension or Pane. The type check of a component's shape stays as the safety net for a build that names the right version but the wrong shape. Update checks and any catalog never offer a version this Pane cannot run, and say when an update needs a newer Pane (#127).

**Breaking changes are announced and grouped.** Each Pane release that changes the API lists what changed under a "Breaking changes" heading in its release notes, with code before and after. Breaking changes are gathered into deliberate API versions, never shipped in a patch release. Official extensions are released for a new API version before the Pane release that requires it, and that release pins them.

**Rejected.** Pi's way, no version and no check: an incompatible extension loads and fails later, mid-use. Keeping 0.x free to change shape until 1.0: acceptable while every extension lived in Pane's repository, not once authors outside it build against the API. Supporting every past version indefinitely: ADR 0010 rejects that obligation.
