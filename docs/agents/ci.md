# CI: verification tiers and pacing

All verification that gates a merge happens on GitHub Actions, paced in tiers so that no work waits for a run it does not need. Local commands are each developer's own choice — never required, never assumed, never a substitute: a branch is done when its CI tier is green.

## Which workflow runs when

| Event | Workflow | What runs |
|---|---|---|
| Push to `pi-subagent/**` | `ci-fast.yml`, quick tier | `Check (os)`: `cargo fmt --all --check` and `cargo check --workspace --all-targets` on Linux and Windows; the JS/TS samples rebuilt if stale; the `pane.json` schema regenerated if stale |
| Manual run with `verify` on a `pi-subagent/**` branch | `ci-fast.yml`, verify tier | `Lints (os)` and `Tests (os, N/3)` on Linux and Windows, `Check (macos-15)` |
| Manual run with `tests` on any branch | `ci-fast.yml`, chosen tests | `Chosen tests (os)` on Linux, Windows and macOS |
| Push to any other branch except `main`; a pull request from a fork | `ci-branch.yml` | `Lints (os)` on Linux, Windows and macOS; `Tests (ubuntu-24.04, N/3)`, shard 2 also running the file index's regression guard. A push or fork pull request that changes only documentation runs nothing but the summary |
| Push to `main`; manual run | `ci.yml`, the release matrix | Lints and tests on all three systems, smokes, packages, renderer output, JS/TS guests from source, licenses |

Every workflow ends in one job named **`CI passed`**: green when every other job of the run passed or was skipped, red when one failed or was cancelled. That is the check to require in branch protection. Jobs and shards can then change without the protection changing with them. A job added to a workflow is also added to its `CI passed` job's `needs`. A pull request from this repository's own branches also triggers `ci-branch.yml`, but that run verifies nothing (its branch's push run does), and its summary is named `CI passed (see the push run)` so it never stands in for the push run's.

## The tiers

- **`ci-fast.yml` — ticket worktrees (`pi-subagent/**`).** A plain push runs the quick compile check on Linux and Windows. A manual run, `gh workflow run ci-fast.yml --ref <branch> -f verify=true`, runs the full check leg instead. `Lints (os)` runs `cargo xtask ci-lints` (formatting, the committed `pane.json` schema, the prebuilt-samples check, `cargo xtask sdks`, clippy `-D warnings`). `cargo xtask sdks` checks that the SDKs package as they would be published, publishing nothing: the Rust SDK's copy of `wit/` matches it, `cargo publish --dry-run` packages and builds `pane-extension`, and `npm pack` packs `@pane-app/extension` — carrying the generated `pane.json` schema with it. The schema check regenerates the schema from pane-core's manifest types and compares it with the committed copy, so the two cannot drift apart. Publishing them is a person's step, never CI's. Beside it, `Tests (os, N/3)` runs the guests and the workspace tests under cargo-nextest with two retries, in three shards that run at once. A macOS leg compiles the macOS-gated code (the autostart, tray, placement and hotkey adapters, which the Linux and Windows legs never compile) and runs the macOS clipboard adapter test. An implementer iterates on plain pushes and asks for a verify run once, when it believes the branch is done. It makes no commit to ask: the old `[verify]` commit-message trigger left empty retry commits on `main`, and is gone. A superseded run is cancelled automatically, so iterating is cheap. A plain push whose committed JS/TS sample components (`guests/prebuilt`) no longer match their sources, the SDK, the WIT or the toolchain also rebuilds them on Linux with `cargo xtask js-guests` — pane-build's JavaScript build (#218), which needs Node.js and npm and the repository's own Rust (the componentizer linked in), and no Python, nightly Rust, wasi-sdk or toolchain cache. It uploads them as the `js-guests` artifact. The implementer commits that artifact (`gh run download <run> -n js-guests -D guests/prebuilt`) before asking for a verify run, whose prebuilt-samples check would otherwise fail. A plain push whose committed `pane.json` schema (`guests/js/schema`) no longer matches what Pane's manifest types generate likewise regenerates it and uploads it as the `manifest-schema` artifact, to be committed the same way (`gh run download <run> -n manifest-schema -D guests/js/schema`).
- **`ci-branch.yml` — every other branch push, and pull requests from forks.** `Lints (os)` runs on Linux, Windows and macOS. Clippy also type-checks the code only that system compiles. `Tests (ubuntu-24.04, N/3)` runs the guests and the tests in three Linux shards; shard 2 then runs the file index's regression guard (below). The wall time is the slowest job. The full test suite on Windows and macOS runs at the verify tier and in the release matrix, not per push. A push whose branch differs from `main` only under `docs/` or in top-level Markdown files skips every job but the summary. The branch is compared with its merge base on `main`, not with the previous push, whose run may have been cancelled.
- **`ci.yml` — the release matrix.** It runs `Lints (os)` and `Tests (os, N/3)` on all three systems, `Smoke (os)`, `Package (os)` in its own job beside the smoke, renderer output, JS/TS guests from source (a rebuild job, then the tests in three shards), and licenses. It runs on pushes to `main` and on demand (`workflow_dispatch`), and nowhere else: not on branch pushes, not on pull-request events. It verifies a release, not a milestone: its evidence feeds the milestone's release-validation ticket (for #70, #84) when a release is actually made.
- **`cli-packages.yml` — Pane's npm packages for extension authors (#219, #215, spec #128).** It runs on demand and on any push that changes the packages (`packages/cli`), the toolchain (`tools/componentize-js`), the CLI and what it builds from (`crates`, `wit`, the SDK, the sample it checks, the lockfiles). `Wasm parts` builds `runtime.wasm` and takes wasi-sdk's WASI 0.3 `libc.so` once, on Linux (`cargo xtask wasm-parts`, what `pane_js.py` did before #219 retired it), recording their digests — and compares them with the committed parts (`cargo xtask check-parts`) that the repository's JS/TS builds embed and the platform packages ship, so those cannot drift from the vendored source. Then `Package (target)` builds `pane-ext` and the componentizer for Windows, macOS and Linux on x64 and arm64 (`cargo xtask cli-package`, which verifies the committed parts' digests and assembles the two packages), packs the tarballs `npm pack` makes, checks them the way their users get them — installed into a scratch project with nothing but Node.js and npm, building the TypeScript sample, first with the CLI's own linked componentizer and then with the platform package's (`PANE_COMPONENTIZER`, the same path an installed Pane's development mode spawns) — and uploads the tarballs as the `npm-cli` and `npm-cli-<target>` artifacts. Publishing them is a person's step, never CI's. It is not a merge gate, and no other tier waits for it.

## Rechecking a few tests

To recheck fixes without the whole suite, name the tests in a manual run on the branch: `gh workflow run ci-fast.yml --ref <branch> -f tests='test(/file_index/)'`. It builds the guests and runs only the tests that nextest filter expression selects, on Linux, Windows and macOS, with the same opt-ins as every test job. The full verify run (or the branch tier) still decides that a branch is done. A manual run needs the workflow on `main`. Locally, `cargo xtask ci-tests -E '<filter>'` does the same; options after `ci-tests` go to `cargo nextest run`.

To recheck a fix to the release matrix's other jobs, a smoke for instance, name the jobs in a manual run: `gh workflow run ci.yml --ref <branch> -f only=smoke` (comma-separated with no spaces: `renderers`, `licenses`, `lints`, `tests`, `smoke`, `package`, `js-guests`). A platform-specific smoke fix can add `-f smoke_os=macos-15` (or `windows-2025` / `ubuntu-24.04`); the default `all` and pushes to main still run every system. The jobs not named are skipped, so its `CI passed` answers only for those named; a release still needs a run of everything.

## How the jobs are built

- **One setup.** Every job that runs cargo starts with the composite action `.github/actions/setup`. It installs the Linux build dependencies and mold, then installs the pinned toolchain from `rust-toolchain.toml` and uninstalls every other toolchain. It then restores the Rust cache. For test jobs (`tests: true`) it also installs the pinned cargo-nextest and sets the opt-ins: `PANE_TEST_PROCESS_TREES` everywhere, `PANE_TEST_REAL_CLIPBOARD` on Windows and macOS, `PANE_TEST_SYSTEM_ICONS` on Windows. On Windows it moves `TMP`/`TEMP` to a faster drive: the D: drive if the runner has one, else a Dev Drive made for the job, else C: with a warning. The drive is given a change journal as C: has (the runner's D: keeps none), since the file index tests catch up from it after a restart. A change to how jobs are set up is made there, once.
- **One Rust cache per operating system.** All jobs share one `rust-cache` entry per system (`shared-key: pane`). Only `ci.yml`'s `Lints (os)` on `main` saves it. On `main` that job also builds the guests and the tests without running them (`cargo xtask ci-tests --no-run`), so the entry holds what clippy, the test builds and the guest builds reuse. Every other job, on every branch and pull request (forks included), only restores what `main` saved. Before this, each job saved its own entry. The entries outgrew the repository's 10 GB and evicted each other, and about half the Rust jobs started with no cache. The runner image's own stable Rust is uninstalled because rust-cache hashes every installed toolchain into its key, and an image update would otherwise start every cache again. A new Cargo workspace whose build should be cached is added to the action's `workspaces`.
- **Shards.** `cargo xtask ci-tests --partition hash:N/3` runs one shard. nextest places each test in a shard by a hash of its name, so a new test needs no list kept up to date. Each shard builds the tests itself from the restored cache. Those builds run at the same time; an archive of the test binaries built once would instead put its upload and download on the critical path. In `.config/nextest.toml`, the longest test (`memory_peaks`, about 150 s) has a priority, so it starts first in its shard.
- **One compiled-code cache per run.** `.cargo/config.toml` sets `PANE_TEST_CODE_CACHE` to `target/test-code-cache`. Every extension runtime a test starts then keeps compiled guest code there, not in its own cache folder. A run therefore compiles each component once, not once per test, and before this the JS/TS tests spent most of their time compiling the 4 MB QuickJS component. The cache is safe across nextest's parallel processes: Wasmtime writes each entry whole and renames it into place. `runtime_cache.rs`'s caching test opts out (`Runtime::ignore_shared_code_cache`), so it still checks a caller's own folder. Set the variable empty to make every runtime compile again.
- **The Linux clipboard test** runs under Xvfb in shard 1 of the Linux tests, as `cargo nextest run -E 'binary(clipboard_adapter_linux)'`, reusing that shard's build.
- **The file index's regression guard** (#183) runs in shard 2 of `ci-branch.yml`'s Linux tests, after the tests, as `cargo xtask file-index-guard`. It runs the file index's benchmark (`crates/pane-core/examples/file_index_bench.rs`) over a generated tree of about 20,000 entries, one run, with the walk at normal priority. The benchmark is built in the development profile, as the tests built it (`cargo build --workspace --examples` reuses their build, found under `CARGO_TARGET_DIR` or `CARGO_BUILD_TARGET_DIR` if set, else `target`), not in release, which would build every dependency again. With `--guard` it fails when a measure is over its ceiling: the first index (180 s), the index on disk (400 B per entry), the 95th percentile of each kind of query and of all of them, on one segment and on several segments with changes in memory, the background merges held off (2.5 s), and each re-index row's 95th percentile: near the root, and in a deep folder with the folders above kept and with nothing kept (2.5 s). The ceilings are the benchmark's `GUARD_*` constants. They are set for that unoptimized build on a shared runner, far above what it should take, so they catch only a large regression (a query or a change gone quadratic, an index several times larger), never a slow runner. The guard prints the whole report, so its log shows the numbers to tighten them by. The benchmark's real numbers come from `cargo xtask file-index-bench` in release, on demand. Neither `ci-fast.yml` nor the release matrix runs the guard.
- **The resource workload.** `Smoke (ubuntu-24.04)` runs `scripts/measure-linux.sh` after the smoke, on the same runner with the same binary and guests ([resource measurements](../research/resource-measurements.md)). Since #189 it includes the hidden phases, which depend on the smoke: they serve the default extensions' payloads the smoke left in `target/dist/artifacts` (with the index's `application` entry left out, so the 99.0.0 package the smoke built is not offered), wait for the five defaults to be recorded (usually well under a minute, at most 600 s), settle 30 s and sample 60 s hidden. That adds about two minutes to the job, and at most about twelve. Without the payloads (the workload run on its own, without `cargo xtask package-linux --dev`) the hidden phases are skipped and reported so, and the rest of the workload runs and is checked as before.

## How merges are paced

- Land each ticket on the milestone branch as one commit: `git merge --squash <ticket-branch>`, then a commit titled for the ticket with its number (`… (#NN)`) and a body saying what it does, signed off. The ticket branch's iterations, fixups and merges stay on the ticket branch, out of `main`'s history; the ticket's results comment cites the squashed commit. A ticket whose branch is already a curated series may keep it.
- A milestone's pull request to `main` lands with a merge commit, so the commits its tickets cite stay reachable; the repository does not offer rebase merging, which would rewrite them. A small pull request that is not a milestone lands squashed.
- Land ticket merges in waves of 3–4 with a single final push. Pushes to a branch auto-cancel superseded runs, and a green run on the newest commit verifies every ancestor: intermediate pushes cost nothing.
- Do not dispatch the release matrix on a ticket branch, and do not wait for any release leg during a milestone. The branch tier is the merge gate.
- Poll runs with small commands (`gh run list --branch <branch> --repo pane-app/pane`), never long sleeps.
- When a change alters what a leg runs or how long it takes, update this file with it.

## Flakes

One test fails occasionally without a code cause: `command_search.rs`'s `a_service_that_stalls_is_given_up_on_within_the_limits` under runner load. The tests run under cargo-nextest with two retries, which absorbs it. (`update.rs`'s claim-window test, once a macOS flake, now holds the update inside its claim and no longer races the copy.) A failure that survives its retries is real: rerun the failed jobs once (`gh run rerun <id> --repo pane-app/pane --failed`) before diagnosing.

The Linux clipboard adapter test (`clipboard_adapter_linux.rs`'s `the_watcher_reports_this_tests_changes_until_dropped`) runs in its own Xvfb step. Once (release run 37426152516) Xvfb reset the test's first connection ("Pane could not reach the X11 display :99: Connection reset by peer"), before any clipboard work. That panic is the display, not the adapter. The step now runs under cargo-nextest with two retries, which should absorb it; if it still fails, rerun the failed job.

## What is traded

Per branch push, Windows and macOS get lints only; their full test runs happen at the verify tier and in the release matrix. The release legs — the app actually launched and screenshotted, the packages built, the renderer's output checked — never run per push: a milestone's native and visual validation is its own open release-validation ticket, fed by the run on `main`.
